# Old Calculator

Securinets · crypto · автор: [kristoferUA](https://github.com/kristoferUA)

[English](README.md) · [Українська](README.uk.md)

[Локальний інстанс](docs/instance.uk.md) · [Протокол](reference/PROTOCOL.md) · [Публікація на GitHub](docs/publishing.md)

Old Calculator надає арифметичні операції над прихованими масивами входів і виходів та просить визначити функцію. Остаточний розв'язок пакує дві повні пари в один точний двійковий дріб, читає його через калькулятор і локально відновлює поточну функцію. На раунд потрібно **45 арифметичних операцій**. Цим способом пройдено всі **16 раундів**.

Флаг:

```text
Securinets{ed9a482110a5a6936482e700155f811742f97a04decfa75d3cee28bca77239c1}
```

## Запустити задачу локально

У репозиторії є Linux Docker-інстанс, режим записаної сесії та локальний солвер. З кореня репозиторію:

```bash
cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T --workdir /tmp calculator \
  python /app/solve.py --run --host 127.0.0.1 --trace /tmp/local_trace.jsonl
```

Випадковий і записаний режими вже пройдено на всі 16 раундів. Записаний режим також відтворив усі 16 запитань із показаними значеннями з дослідженої сесії. Команди Docker Engine, імпорт готового образу й налаштування описані в [інструкції інстансу](docs/instance.uk.md).

Кореневий `solve.py` за замовчуванням підключається до `127.0.0.1`. Побайтова копія початкового віддаленого солвера збережена в [solvers/solve_remote_original.py](solvers/solve_remote_original.py).

## Інтерфейс задачі

Адреса інстансу під час розв'язання:

```text
nc calculator-crypto.securinets.tn 4873
```

Сервіс зберігає два масиви `x` та `y`, по 100 елементів у кожному. Початкові значення приховані. Можна додавати й множити елементи, виконувати ці операції з константою та записувати результат у вибрану комірку.

Потрібні формати запитів:

```json
{"operation":"add","source":["x","y"],"source_index1":0,"source_index2":1,"destination":"x","dest_index":98}
{"operation":"mult","source":["x","y"],"source_index1":0,"source_index2":1,"destination":"x","dest_index":98}
{"operation":"add_const","source":"x","index":0,"const":1,"destination":"x","dest_index":98}
{"operation":"mult_const","source":"x","index":0,"const":2,"destination":"x","dest_index":98}
{"operation":"submit","source":"x","index":98}
```

Кожен рядок тут є окремим запитом. Перш ніж надсилати наступну операцію, клієнт чекає нового запрошення. Успішна арифметична операція повертає:

```text
{"result": "Operation successful"}
Enter JSON:
```

`submit` показує значення однієї комірки й запускає фінальне запитання поточного раунду. Правильна відповідь переводить сервіс до наступного раунду. Після шістнадцяти правильних відповідей він повертає флаг.

## Що вдалося встановити зі спостережень

Серед наданих матеріалів не було вихідного коду сервера. Метод побудовано за описом взаємодії та отриманими відповідями.

Модель, з якою вдалося пройти задачу:

$$
y_i=f(x_i)=ax_i+b,
\qquad a,b\in\{1,\ldots,16\},
\qquad x_i\in\{0,\ldots,255\}.
$$

Коефіцієнти потрібно відновлювати заново в кожному раунді. Функція, яка підходила для одного раунду, могла не підходити для наступного.

Поведінка арифметики та виведення була не менш важливою за саму формулу:

- Проміжні значення автоматично не зводяться за модулем 256.
- Великі цілі та від'ємні значення відхиляються під час спроби їх показати.
- Ця версія приймає константу `0.5` і показує невеликі дробові значення.
- Оновлений формат, з яким працює солвер, окремо показує вибрану комірку та випадковий аргумент перевірки.

Солвер обробляє таке запитання:

```text
the value of x[98] you submitted is: <selected value>
As a final Test please give the value after applying the secret operation of the random number <t>:
{"y" : number }
```

У вибраній комірці міститься наша закодована інформація. Фінальна відповідь — це `f(t)` для окремого числа `t` з наступного рядка. Якщо переплутати ці два значення, відповідь буде неправильною.

Цей врайтап описує оновлений формат. На початку розв'язання запитання було менш однозначним; доданий солвер очікує рядок зі значенням вибраної комірки.

## Як ми прийшли до цього підходу

Перші спроби допомогли відокремити приховану функцію від арифметичного інтерфейсу:

| Спроба | Спостереження | Висновок |
| --- | --- | --- |
| Записати нуль і виконати `submit` | Фінальна відповідь усе одно могла бути ненульовою | Зміна комірки не перевизначає приховану функцію |
| Побудувати код коефіцієнтів, припускаючи байтову арифметику | Код не відновив очікувані коефіцієнти | Не можна моделювати запис як зведення за модулем 256 |
| Показати велике проміжне ціле число | Сервіс повідомив його бітову довжину та відхилив читання | Зберігання й виведення мають різні обмеження |
| Показати від'ємну різницю | Сервіс відхилив від'ємне значення | Для читання потрібне придатне невід'ємне значення |
| Масштабувати запаковане ціле множенням на `0.5` | Невеликий дріб зберіг потрібну інформацію | Точні двійкові дроби дали остаточний спосіб читання |

Важливою була й зміна запитання: вибрана комірка та випадковий аргумент перевірки стали явно відокремленими. У ранніх припущеннях випадковий аргумент іноді сприймався як прочитане значення комірки. Остаточний метод читає з комірки дані для відновлення функції, а потім обчислює її значення для окремого аргументу перевірки.

## Чому достатньо двох пар

Для двох різних входів коефіцієнти афінної функції визначаються формулами:

$$
a=\frac{y_1-y_0}{x_1-x_0},
\qquad b=y_0-ax_0.
$$

Коли дві пари вже є на нашому боці, знайти `a,b` нескладно. Основна проблема — прочитати обидві приховані пари за одну прийняту операцію `submit`.

Корисне спостереження: невеликий дріб може зберігати всі їхні значущі біти. Обмеження величини числа не обмежує інформацію в дробі вісьмома бітами.

## Пакування двох пар у 42 біти

Беремо початкові пари з індексами `0` та `1` і не змінюємо їх під час обчислення.

Для кожного входу достатньо 8 бітів. Вихід має таку межу:

$$
0\le y_i\le16\cdot255+16=4096<2^{13}.
$$

Отже, кожному виходу достатньо 13 бітів. Дванадцяти було б замало для граничного значення `4096`.

Чотири поля займають 42 біти:

```text
| x0: 8 бітів | y0: 13 бітів | x1: 8 бітів | y1: 13 бітів |
```

Будуємо ціле число:

$$
M=\bigl((x_0\,2^{13}+y_0)\,2^8+x_1\bigr)\,2^{13}+y_1.
$$

За побудовою:

$$
0\le M<2^{42}.
$$

Калькулятор може зберегти це велике проміжне число. Перед `submit` його потрібно перетворити.

Великі множники складаються з невеликих дозволених констант:

```text
8192 = 128 * 64
256  = 128 * 2
```

Перші десять операцій еквівалентні таким обчисленням:

```python
scratch = x[0] * 1
scratch *= 128
scratch *= 64
scratch += y[0]
scratch *= 128
scratch *= 2
scratch += x[1]
scratch *= 128
scratch *= 64
scratch += y[1]
```

Клієнт перетворює ці рядки на описані JSON-запити, зберігаючи проміжний результат у `x[98]`.

## Як зменшити число без втрати бітів

Множимо запаковане значення на `0.5` рівно 35 разів:

$$
v=\frac{M}{2^{35}}.
$$

Тепер воно потрапляє в діапазон:

$$
0\le v<\frac{2^{42}}{2^{35}}=128.
$$

Таку величину сервіс дозволяє показати. Водночас усі запаковані дані зберігаються точно:

1. Binary64 має 53 біти точності значущої частини; числу `M` потрібно не більше 42.
2. Ділення на степінь двійки змінює двійковий порядок, не відкидаючи значущі біти в цьому діапазоні.
3. Значення залишаються далеко від межі втрати малих чисел під час обчислень.

Десятковий текст відповіді також має дозволяти відновити початкове двійкове значення. Успішний серверний вивід це забезпечував; солвер перевіряє точність перед початком основних раундів.

Повна кількість операцій:

```text
10 операцій для пакування двох пар
35 множень на 0.5
---------------------------------
45 арифметичних операцій на раунд
```

## Спочатку перевіряємо точність читання

Солвер починає з окремого з'єднання для перевірки. Він будує найбільше 42-бітне слово:

$$
M_{\max}=2^{42}-1=4398046511103.
$$

Очікуваний рядок після масштабування:

```text
127.9999999999709
```

Після декодування мають відновитися початкове слово та штучні поля `(255,8191),(255,8191)`. Це перевіряє всі 42 біти, включно з тими, які можуть не використовуватися у звичайному невеликому прикладі.

Після цього з'єднання закривається на фінальному запитанні. Запис відомих значень у масиви не змінює приховану функцію сервера, тому ця перевірка не відповідає на запитання про її значення.

## Відновлення запакованих полів

Читаємо відповідь і повертаємо двійковий порядок назад:

```python
scaled = math.ldexp(float(selected_value), 35)
```

Результат `scaled` має бути цілим і меншим за `2**42`. Потім поля виділяються від молодших бітів до старших:

```python
import math

def unpack(selected_value):
    value = float(selected_value)
    if not math.isfinite(value) or not 0 <= value < 128:
        raise ValueError("invalid selected value")

    scaled = math.ldexp(value, 35)
    if not scaled.is_integer():
        raise ValueError("the printed fraction lost required precision")
    word = int(scaled)
    if not 0 <= word < 2**42:
        raise ValueError("unexpected packed width")

    y1 = word & 8191
    word >>= 13
    x1 = word & 255
    word >>= 8
    y0 = word & 8191
    word >>= 13
    x0 = word & 255
    return [(x0, y0), (x1, y1)]
```

## Відновлення поточної функції

Якщо входи різні, формула нахилу визначає `a,b`. Доданий солвер також використовує невеликі дозволені діапазони коефіцієнтів, щоб однаково обробляти всі декодовані випадки:

```python
def coefficients(points):
    x0, y0 = points[0]
    possible = []
    for a in range(1, 17):
        b = y0 - a*x0
        if 1 <= b <= 16 and all(a*x+b == y for x, y in points):
            possible.append((a, b))
    return possible
```

Має залишитися рівно одна пара. Якщо обидва входи однакові, межі коефіцієнтів іноді все одно визначають єдину відповідь. В іншому разі клієнт закриває неоднозначну сесію та починає нове з'єднання в межах заданої кількості спроб.

Порожній список кандидатів означає, що декодовані значення не відповідають прийнятій моделі; солвер повідомляє про цю невідповідність.

## Проходження всіх 16 раундів

Для кожного раунду:

1. Побудувати запакований дріб у `x[98]` за 45 арифметичних запитів.
2. Виконати `submit` для `x[98]` і прочитати дріб та новий аргумент перевірки `t`.
3. Декодувати дві пари та визначити єдині `a,b`.
4. Надіслати `{"y": a*t+b}`.
5. Дочекатися наступного раунду або фінального флага.

Читач відповідей зберігає постійний буфер байтів. Він шукає завершені запрошення й залишає непрочитаний хвіст, оскільки TCP може доставляти відповідь частинами або поєднати кілька фрагментів в одному читанні.

## Фінальний раунд початкового розв'язання

У фінальному раунді отримано:

```text
selected value = 30.055107453401433
test input     = 228
```

Точне відновлення дає:

$$
M=1032685628721,
$$

```text
(x0,y0) = (60,902)
(x1,y1) = (225,3377)
```

Тому:

$$
a=\frac{3377-902}{225-60}=\frac{2475}{165}=15,
$$

$$
b=902-15\cdot60=2,
\qquad f(228)=15\cdot228+2=3422.
$$

Фінальна відповідь клієнта:

```json
{"y":3422}
```

Сервер повернув флаг, наведений на початку врайтапу. Числові дані збережені в [examples/round16.json](examples/round16.json), а підписаний уривок діалогу — в [examples/success.txt](examples/success.txt).

## Запуск солвера та офлайн-прикладу

Docker-образ використовує Python 3.12. Солвер і допоміжний інструмент потребують лише стандартної бібліотеки.

Вбудована локальна арифметична перевірка солвера доступна командою:

```bash
python3 solve.py --self-check
```

Вона охоплює 2 048 афінних випадків, точне двійкове відновлення та потрібні поля запитання. Розрахунок фінального раунду початкового розв'язання можна відтворити без підключення:

```bash
python3 tools/packing_demo.py
```

Запуск клієнта з хоста для вже запущеного локального інстансу:

```bash
python3 solve.py --run --host 127.0.0.1 --port 4873 --trace local_trace.jsonl
```

Явний вибір зафіксованої адреси змагання:

```bash
python3 solve.py --run --host calculator-crypto.securinets.tn --port 4873 --trace remote_trace.jsonl
```

Параметр `--trace` очікує назву файла. Запити й відповіді зберігаються у форматі JSON Lines. Типово солвер проходить 16 раундів і дозволяє до трьох сесій, якщо пари неоднозначні. Для записаного локального сценарію використовуй `--sample-indices 0 99`.

Сценарій у `fixtures/recorded_session.json` походить з окремого дослідження живого сервера 21 жовтня 2026 року. Його коефіцієнти та показані значення відрізняються від початкового розв'язання вище. Локальний записаний режим відтворює саме цю пізнішу сесію.

## Примітки

Метод залежить від арифметики та формату виведення цієї версії Old Calculator: точного двійкового масштабування, приймання `0.5` і достатньої кількості цифр для відновлення `float`. Початкові приховані пари також мають вкладатися у вибрану ширину полів.

У [специфікації живого протоколу](reference/PROTOCOL.md) підтверджені спостереження відділені від невстановлених деталей. Локальний сервіс відтворює записаний діалог та арифметику; точний генератор випадкових чисел і розподіли оригіналу залишаються невідомими. Явні рішення локальної реалізації описані в [інструкції інстансу](docs/instance.uk.md).

Структура пакета відповідає оформленню авторського [врайтапу Kuliah67 Archive](https://github.com/kristoferUA/COMPFEST-CTF-2026-writeups/tree/main/COMPFEST18-kuliah67-archive-writeup).
